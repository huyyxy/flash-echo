# 极轻量高并发“垫话/过渡词模型”需求与架构设计方案

在实时语音交互（如语音助手、智能客服、实时对话数字人）场景中，主大语言模型（Main LLM）的首字延迟（TTFT, Time to First Token）通常在数百毫秒至数秒之间，这会导致用户在说话结束后感到明显的停顿与迟钝。

为了消除这种“尴尬的沉默”，本项目拟构建一个**极轻量、高并发的“垫话/过渡词模型”（Filler Words Model）**。当用户结束说话后，该模型在数毫秒内做出决策，输出符合当前意图与助理角色设定的垫话前缀，供下游系统播放并作为主模型续写的起点，从而平滑对冲主模型的首字延迟。

---

## 1. 数据定义与数据工程

本着“极轻量、低延迟”的原则，模型的数据流和输入输出进行如下精简设计。

### 1.1 输入数据定义
系统决策阶段接收两个核心输入，**不依赖历史上下文和声学特征**：
1.  **当前用户 Query 文本**：ASR（语音识别）实时输出的完整文本（例如："你觉得人工智能未来会毁灭人类吗？"）。
2.  **助理角色分类标签（Persona Tag）**：当前系统配置的 AI 助理属性，属于静态配置传入。例如：
    *   `male_white_collar`（中年男白领）
    *   `female_receptionist`（前台女助理）
    *   `grandpa`（老爷爷）
    *   `young_girl`（女童）

其中，**是否触发垫话只由 Query 决定，与 Persona 无关**。Persona 只影响触发后最终选择哪一句具体垫话，例如同样是 `THINKING` 类型，`grandpa` 和 `young_girl` 会使用不同风格的话术。

### 1.2 输出数据定义
模型不直接生成复杂的垫话文本（直接生成会增加模型体积与推理延迟，且难以控制幻觉），而是输出**结构化标签**：
1.  **触发决策（Trigger Decision）**：是否触发垫话。
    *   `0`: 不触发（例如简单 Query "一加一等于几"、短确认 "好的"、结束语 "再见"。这类问题需要直接快速回答，垫话会显得拖沓）。
    *   `1`: 触发（例如复杂问题、开放性讨论、需要检索或需要组织表达的请求，需要用垫话平滑主模型首字延迟）。
2.  **垫话功能类别（Filler Type）**：若触发，预测最合适的垫话功能类别；若不触发，统一输出 `NONE`。
    *   `NONE`（不触发）：简单事实问答、短指令、寒暄结束语、重复性低价值 Query。
    *   `ACKNOWLEDGE`（承接确认型）：用户提出明确任务、请求或指令，垫话用于表示“已接收到请求”。示例 Query："帮我写一封请假邮件"、"给我规划一下周末行程"。
    *   `THINKING`（思考缓冲型）：用户问题需要推理、比较、解释或计算，垫话用于争取组织答案的时间。示例 Query："为什么有些公司现金流很好但利润很差？"。
    *   `FRAME`（结构铺垫型）：用户提出开放性、观点型、方案型问题，垫话用于自然引出后续结构化回答。示例 Query："你怎么看 AI 对教育行业的影响？"。
    *   `EMPATHY`（情绪承接型）：用户表达情绪、压力、困惑或主观感受，垫话用于先接住情绪，再进入回答。示例 Query："我最近真的很焦虑，不知道怎么办"。
    *   `RETRIEVAL`（检索/回忆型）：用户请求查询、查找、总结已有材料或回忆上下文事实，垫话用于提示正在查找或整理信息。示例 Query："帮我看看上次会议里说的截止时间是什么"。
    *   `CLARIFY_LEADIN`（澄清引导型）：用户 Query 信息不足、指代不明或存在多种解释，主回复大概率需要先问澄清问题，垫话用于自然引出澄清。示例 Query："那这个怎么弄？"。

标签设计原则：
*   **先判断是否触发，再判断触发类型**。`Trigger=0` 时 `Filler Type` 必须为 `NONE`。
*   **类型标签表示“垫话的功能”，不表示具体措辞**。具体话术由 `Filler Type + Persona Tag` 在模板库中选择。
*   **类型互斥，采用优先级消解冲突**：`EMPATHY` > `CLARIFY_LEADIN` > `RETRIEVAL` > `ACKNOWLEDGE` > `FRAME` > `THINKING` > `NONE`。例如既有情绪又有开放问题时优先标为 `EMPATHY`；既需要查找又需要推理时优先标为 `RETRIEVAL`。

预测出 `Filler Type` 后，结合 `Persona Tag`，通过**静态配置字典（Templates Registry）**随机抽取对应的具体话术：

| 助理角色 (`Persona Tag`) | 垫话类别 (`Filler Type`) | 候选垫话话术示例 |
| :--- | :--- | :--- |
| `grandpa` (老爷爷) | `THINKING` | "这事让我想想。"；"我琢磨一下。" |
| `young_girl` (女童) | `THINKING` | "我想想看哦！"；"让我想一下下！" |
| `female_receptionist` | `ACKNOWLEDGE` | "好的，明白您的意思了。"；"好的，我了解了。" |
| `male_white_collar` | `FRAME` | "关于这个问题，"；"这个问题可以这样看，" |

垫话文本定义为主回复的**第一句话前缀**，截断边界为第一个逗号、句号或感叹号（含标点）之前的内容。模板配置时应直接保存这个可播放前缀，后续主大模型需要在该前缀之后继续生成完整回复，而不是把垫话视为独立的、与主回复无关的音频片段。

### 1.3 数据集建设与语料合成
为了训练分类模型，需要构建包含 `(Query, Trigger_Label, Type_Label)` 的数据集，并单独维护 `(Persona, Type_Label, Template_Text)` 模板库。
*   **语料来源**：
    *   收集现有的高频用户问题列表（常见 QA 集、闲聊数据集、任务型对话数据集）。
*   **LLM 标注与合成方案**：
    *   使用具有 OpenAI 兼容接口的商业或开源大模型（如 GPT-4o、Qwen-Max），编写 Prompt 对现有问题进行批量标注。
    *   **Prompt 任务一（分类）**：判断 Query 是否需要触发垫话，并判断最适用的垫话功能类别（`NONE`/`ACKNOWLEDGE`/`THINKING`/`FRAME`/`EMPATHY`/`RETRIEVAL`/`CLARIFY_LEADIN`）。
    *   **Prompt 任务二（增强）**：对高频问题进行同义改写（Paraphrasing），扩展文本泛化能力。
    *   **Prompt 任务三（一致性校验）**：对同一 Query 的多次标注结果进行一致性检查；若 `Trigger_Label` 或 `Type_Label` 不一致，进入人工复核集。
*   **Template 生成**：让大模型根据不同 Persona 设定，分别撰写各 50+ 条的各类垫话模板，存入系统配置。模板必须满足“第一句话前缀”约束，且能被主模型自然续写。

## 2. 模型选型评估

针对高并发、极低延迟的要求，我们对以下两种方案进行评估：

| 评估维度 | 方案 B: 轻量级文本分类器 (FastText / TextCNN) | 方案 C: 蒸馏小 Transformer (TinyBERT / MiniLM ONNX) |
| :--- | :--- | :--- |
| **推理延迟 (CPU)** | **极佳 (1 ~ 3 ms)** | **优秀 (3 ~ 8 ms)** |
| **模型体积** | 极小 (< 5MB) | 较小 (15MB ~ 50MB) |
| **语义理解与泛化能力** | 较差（极度依赖字词精确匹配，同义词泛化差） | **极佳**（具备深层语义表征，能理解未见过的相似问法） |
| **在线集成复杂度** | 较低，但需要额外设计特征工程和阈值规则 | **较低**（Query 直接输入模型，Persona 仅用于模板检索） |
| **高并发部署** | 极高并发，资源开销极小 | 高并发，在 ONNX Runtime 优化下开销可控 |

### 🔍 最终选型决策：**方案 C（TinyBERT / MiniLM-L6 的 ONNX 部署方案）**
*   **决策理由**：垫话模型对“是否触发”和“触发后属于哪类功能”的判定需要较强的语义感知能力。例如，"苹果怎么吃"（简单 factual）与 "怎么评价苹果公司的发展"（复杂开放）虽然字面重合度高，但处理逻辑完全不同，FastText 极易误判。
*   **推荐规格**：选择 2 层或 4 层的蒸馏 Transformer 模型（如 `bert-tiny`：2 层，128 隐藏层维度，约 440 万参数）。将其转换为 **ONNX 格式**，在 CPU 上即可稳定实现单次推理 <5ms 的极速响应。

## 3. 特征工程设计

为了保证端到端极速响应，特征工程需进行极致剪裁。

### 3.1 文本特征设计
不进行繁琐的分词、词性标注等前置 CPU 密集型操作，而是直接利用模型的 Tokenizer 进行处理：
*   **模型输入**：仅输入 Query 文本，不将 `Persona Tag` 拼入分类模型。
    *   *拼接格式*：`用户Query`
    *   *示例*：`为什么天是蓝色的？`
    *   模型只学习 Query 到 `Trigger Decision` 和 `Filler Type` 的映射，避免 Persona 干扰触发判断。
*   **Persona 使用位置**：Persona 在模型推理之后进入模板检索阶段，用于从 `Filler Type` 对应的候选模板中选择符合角色风格的话术。

### 3.2 排除的特征说明
*   **无声学特征**：不引入 VAD 停顿时间、说话人语速、音量波动等声学特征，避免前置音频解析带来的延迟，且降低系统复杂度。

## 4. 项目边界与服务接口

本项目只负责“给定用户 Query 和 Persona，判断是否需要垫话，并返回可被下游系统播放和续写的垫话前缀”。ASR、TTS、主 LLM 调用、音频拼接、播放策略和多路并发编排属于上层语音交互系统，不作为本项目的设计范围。

### 4.1 核心输入
服务请求包含以下字段：
1.  **`query`**：必填，ASR 或上游系统输出的用户当前轮完整文本。
2.  **`persona_tag`**：必填，当前助理角色标签，仅用于模板选择，不参与触发分类。
3.  **`request_id`**：可选，用于链路追踪和日志关联。
4.  **`locale`**：可选，默认为 `zh-CN`，用于后续支持多语言模板库。

### 4.2 核心输出
服务响应包含以下字段：
1.  **`trigger`**：是否触发垫话，取值为 `0` 或 `1`。
2.  **`filler_type`**：垫话功能类别。`trigger=0` 时必须为 `NONE`。
3.  **`filler_text`**：最终选中的垫话前缀。`trigger=0` 时为空字符串。
4.  **`template_id`**：模板 ID。`trigger=0` 时为空，用于线上问题回溯和模板级效果分析。
5.  **`model_version`**：分类模型版本，用于灰度、回滚和离线分析。
6.  **`confidence`**：可选，模型对当前标签的置信度，用于后续阈值调优和人工分析。

示例响应：

```json
{
  "trigger": 1,
  "filler_type": "FRAME",
  "filler_text": "关于这个问题，",
  "template_id": "male_white_collar.frame.001",
  "model_version": "filler-cls-v1",
  "confidence": 0.93
}
```

### 4.3 下游集成约定
虽然本项目不负责主 LLM 和 TTS 编排，但输出需要满足下游集成约束：
1.  **垫话文本是主回复前缀**：`filler_text` 应被下游作为主模型回复的已播放前缀，主模型需要从该前缀后继续生成。
2.  **模板边界固定**：`filler_text` 必须截止到第一个逗号、句号或感叹号（含标点），保证可以独立播放。
3.  **避免重复播放**：如果下游主模型输出中包含同一前缀，下游需要在播放或合成前去重。
4.  **不返回音频**：本项目只返回文本、标签和元信息，不负责 TTS 合成，也不返回音频帧。

### 4.4 部署与缓存
1.  **引擎选择**：垫话模型使用 **ONNX Runtime (CPU)** 或 **TensorRT (GPU)** 导出并运行。
2.  **服务形态**：可独立部署为微服务，也可作为上层语音编排服务的本地模块或 Sidecar。
3.  **缓存设计**：
    *   对高频高重复性 Query（如"你好"、"再见"、"你是谁"）建立内存级 KV 缓存。缓存内容为 `(Trigger Decision, Filler Type)`，命中缓存时跳过模型推理。
    *   缓存 Key 应包含归一化后的 Query 和模型版本；Persona 不进入分类缓存 Key，但会进入模板选择 Key。

## 5. 效果评估与验收标准

为了保证该模型可以稳定服务实时语音交互，评估需要覆盖离线分类效果、服务延迟、模板质量和下游可续写性。

### 5.1 离线分类指标
1.  **触发决策指标**：
    *   `Trigger Precision`：建议上线门槛 `>= 95%`。误触发会让简单问题显得拖沓，应优先压低误触发。
    *   `Trigger Recall`：建议上线门槛 `>= 80%`。漏触发只会退化为原始交互体验，风险低于误触发。
    *   按 Query 类型分别统计：简单事实问答、复杂推理、开放观点、任务请求、情绪表达、检索请求、指代不明请求。
2.  **功能类别指标**：
    *   `Type Macro-F1`：建议上线门槛 `>= 85%`。
    *   每个 `Filler Type` 单独统计 Precision/Recall，重点观察 `ACKNOWLEDGE`、`FRAME`、`THINKING` 之间的混淆。
    *   输出混淆矩阵，用于判断是否需要合并或重定义边界不清的类型。
3.  **标注质量指标**：
    *   多轮 LLM 标注或人工抽检的一致性建议 `>= 90%`。
    *   对不一致样本建立 hard cases 集，后续每次模型迭代都必须回归测试。

### 5.2 在线服务指标
1.  **服务端到端延迟**：从服务收到请求到返回结构化响应，包含文本归一化、Tokenizer、模型推理、模板选择和后处理，建议 `p95 < 10ms`，`p99 < 20ms`。
2.  **模型推理延迟**：单独统计 Tokenizer + ONNX 推理耗时，便于定位性能瓶颈。
3.  **缓存命中率**：统计高频 Query 的分类缓存命中率，以及命中后的响应延迟。
4.  **吞吐能力**：按目标并发量压测 `QPS`、CPU 使用率和内存占用，确保 p99 延迟不因高并发明显劣化。

### 5.3 模板与续写质量指标
1.  **垫话自然度**：人工评分 1-5 分，建议平均分 `>= 4.2`，重点评估是否符合 Persona、是否口语自然、是否突兀。
2.  **前缀完整性**：`filler_text` 必须到第一个逗号、句号或感叹号（含标点）结束，自动校验通过率应为 `100%`。
3.  **续写连贯性**：将 `filler_text` 作为主模型已生成前缀进行离线续写测试，人工评估前缀与续写之间是否语义连贯，建议通过率 `>= 95%`。
4.  **重复风险**：离线检查下游续写样本中是否重复包含 `filler_text`，用于验证去重约定和提示词约束是否有效。

### 5.4 模板库验收标准
1.  每个 `Persona + Filler Type` 至少配置 50 条候选模板，避免高频重复。
2.  模板必须满足第一句话前缀约束：到第一个逗号、句号或感叹号为止可以独立播放，且后续可由主模型自然续写。
3.  模板需要按 Persona 做人工审核，避免角色风格混乱、措辞过长、语气过度夸张或不适合 TTS 播放。
4.  模板库需要版本化，线上日志应记录 `template_id`，便于回溯问题样本和做模板级效果分析。
