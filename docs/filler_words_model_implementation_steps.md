# 垫话/过渡词模型实施步骤

本文档基于 `docs/filler_words_model_requirements.md`，将“极轻量、高并发垫话/过渡词模型”的需求拆解为可执行的工程实施步骤。目标是在实时语音交互链路中，以毫秒级延迟完成垫话触发判断、功能类别预测和 Persona 化模板选择，并向下游返回可播放、可续写的文本前缀。

---

## 1. 实施目标与边界确认

### 1.1 实施目标

1. 构建一个输入为 `query + persona_tag`、输出为垫话决策结果的服务或模块。
2. 使用轻量蒸馏 Transformer 分类模型完成 `Trigger Decision` 与 `Filler Type` 预测。
3. 通过模板库将 `Filler Type + Persona Tag` 映射为具体垫话前缀。
4. 支持低延迟、高并发部署，并为灰度、回滚、分析和迭代保留必要元信息。

### 1.2 项目边界

本项目只负责：

1. 接收当前轮用户 Query 与 Persona。
2. 判断是否触发垫话。
3. 返回垫话类型、垫话文本、模板 ID、模型版本和置信度等元信息。

本项目不负责：

1. ASR、VAD、TTS、主 LLM 调用。
2. 音频拼接、播放策略和多路并发编排。
3. 主模型续写去重逻辑，但需要通过接口约定提醒下游处理。

## 2. 阶段一：标签体系与数据规范落地

### 2.1 固化标签枚举

建立统一标签定义，所有数据、训练、推理和日志均使用同一套枚举：

| 字段 | 取值 | 说明 |
| :--- | :--- | :--- |
| `trigger` | `0` / `1` | 是否触发垫话 |
| `filler_type` | `NONE` | 不触发垫话 |
| `filler_type` | `ACKNOWLEDGE` | 承接确认型 |
| `filler_type` | `THINKING` | 思考缓冲型 |
| `filler_type` | `FRAME` | 结构铺垫型 |
| `filler_type` | `EMPATHY` | 情绪承接型 |
| `filler_type` | `RETRIEVAL` | 检索/回忆型 |
| `filler_type` | `CLARIFY_LEADIN` | 澄清引导型 |

约束规则：

1. `trigger=0` 时，`filler_type` 必须为 `NONE`。
2. `trigger=1` 时，`filler_type` 不允许为 `NONE`。
3. 多标签冲突时按优先级消解：`EMPATHY` > `CLARIFY_LEADIN` > `RETRIEVAL` > `ACKNOWLEDGE` > `FRAME` > `THINKING` > `NONE`。
4. `persona_tag` 不参与分类标签标注，只用于模板选择。

### 2.2 定义训练数据格式

建议训练集、验证集、测试集统一采用 JSONL 或 CSV。推荐 JSONL 格式如下：

```json
{"query":"帮我写一封请假邮件","trigger":1,"filler_type":"ACKNOWLEDGE","source":"task_dialog","label_method":"llm_reviewed"}
{"query":"一加一等于几","trigger":0,"filler_type":"NONE","source":"faq","label_method":"llm_reviewed"}
```

字段要求：

1. `query`：当前轮用户完整文本，训练时唯一模型输入。
2. `trigger`：是否触发垫话。
3. `filler_type`：垫话功能类别。
4. `source`：样本来源，便于分桶评估。
5. `label_method`：标注方式，如 `llm_only`、`llm_reviewed`、`human_reviewed`。

### 2.3 建立数据切分策略

1. 按 Query 语义去重，避免同义改写样本同时进入训练集和测试集。
2. 切分比例建议为训练集 80%、验证集 10%、测试集 10%。
3. 测试集需要覆盖简单事实问答、复杂推理、开放观点、任务请求、情绪表达、检索请求、指代不明请求。
4. 维护 hard cases 回归集，用于每次模型迭代后固定回归。

交付物：

1. 标签枚举定义文件。
2. 数据格式说明。
3. 初版训练集、验证集、测试集和 hard cases 集。

## 3. 阶段二：语料收集、标注与增强

### 3.1 收集基础 Query 语料

优先收集以下来源：

1. 现有产品或测试中的高频用户 Query。
2. 通用 FAQ、闲聊、任务型对话和开放问答数据。
3. 手工构造的边界样本，例如短确认、结束语、指代不明、情绪表达、检索请求。

建议初版数据规模：

1. 最小可用训练集：5,000 到 10,000 条。
2. 初版上线候选训练集：30,000 到 100,000 条。
3. 每个非 `NONE` 类型至少 2,000 条有效样本。
4. `NONE` 样本需要保持足够占比，用于压低误触发。

### 3.2 使用 LLM 批量标注

标注 Prompt 需要明确：

1. 只根据 Query 判断是否触发，不参考 Persona。
2. 触发后只选择一个最合适的功能类别。
3. 冲突样本按既定优先级选择。
4. 输出必须是结构化 JSON，便于自动解析。

建议每条样本至少进行两次独立标注：

1. 两次结果一致的样本进入候选训练集。
2. `trigger` 或 `filler_type` 不一致的样本进入复核池。
3. 高频类型混淆样本优先人工复核。

初版标注 Prompt 可参考：

```text
你是实时语音交互系统的数据标注员。请只根据当前用户 Query 判断是否需要播放垫话，并选择一个最合适的垫话功能类别。

输入字段：
- query: 用户当前轮完整文本。

可选标签：
- NONE: 不触发垫话，适用于简单事实问答、短确认、结束语、寒暄等。
- ACKNOWLEDGE: 承接确认型，适用于明确任务、请求或指令。
- THINKING: 思考缓冲型，适用于需要推理、比较、解释或计算的问题。
- FRAME: 结构铺垫型，适用于开放观点、方案设计或需要结构化展开的问题。
- EMPATHY: 情绪承接型，适用于用户表达情绪、压力、困惑或主观感受。
- RETRIEVAL: 检索/回忆型，适用于查询、查找、总结已有材料或回忆上下文事实。
- CLARIFY_LEADIN: 澄清引导型，适用于信息不足、指代不明或存在多种解释的请求。

约束：
1. 只根据 query 判断，不参考 Persona。
2. 如果不触发，trigger 必须为 0，filler_type 必须为 NONE。
3. 如果触发，trigger 必须为 1，filler_type 不能为 NONE。
4. 若多个标签都可能成立，按优先级选择：EMPATHY > CLARIFY_LEADIN > RETRIEVAL > ACKNOWLEDGE > FRAME > THINKING > NONE。
5. 只输出 JSON，不输出解释。

输出格式：
{"trigger":0或1,"filler_type":"标签名","reason":"一句话说明标注依据"}
```

### 3.3 做同义改写增强

对高价值样本做 Paraphrasing 增强：

1. 保持原始意图不变。
2. 覆盖口语、省略、错别字、不同问法和不同长度。
3. 增强样本需要继承原标签，但应抽样人工检查。
4. 避免把过于模板化的合成句大量堆入测试集。

### 3.4 标注质量验收

上线前建议达到：

1. 多轮 LLM 标注或人工抽检一致性 `>= 90%`。
2. `NONE` 与触发类样本边界经过重点抽检。
3. `ACKNOWLEDGE`、`FRAME`、`THINKING` 的混淆样本完成复核。
4. hard cases 集固定版本化保存。

交付物：

1. 标注 Prompt。
2. 标注脚本或批处理任务。
3. 复核池与复核结果。
4. 可训练数据集版本。

## 4. 阶段三：Persona 模板库建设

### 4.1 定义模板库结构

模板库建议使用 JSON、YAML 或数据库配置。初版可使用静态配置文件，结构如下：

```json
{
  "zh-CN": {
    "male_white_collar": {
      "FRAME": [
        {
          "template_id": "zh-CN.male_white_collar.frame.001",
          "text": "关于这个问题，",
          "enabled": true,
          "weight": 1
        }
      ]
    }
  }
}
```

字段说明：

1. `locale`：模板语言或地区，例如 `zh-CN`，用于后续多语言扩展。
2. `template_id`：全局唯一，建议包含 `locale`、`persona_tag` 和 `filler_type`，便于日志回溯。
3. `text`：垫话文本前缀，必须可直接 TTS 播放。
4. `enabled`：是否启用。
5. `weight`：抽样权重，用于降低重复感。

### 4.2 生成模板内容

每个 `Locale + Persona + Filler Type` 至少配置 50 条候选模板。初版至少覆盖 `zh-CN` 下的以下 Persona：

1. `male_white_collar`
2. `female_receptionist`
3. `grandpa`
4. `young_girl`

模板生成要求：

1. 必须符合 Persona 风格。
2. 必须是主回复的第一句话前缀。
3. 必须截止到第一个逗号、句号或感叹号，且包含标点。
4. 不得过长，避免抢占主回复内容。
5. 不得包含事实承诺、检索结果或无法保证的状态。

### 4.3 模板审核与版本化

模板上线前需要检查：

1. 是否自然、口语化、适合 TTS 播放。
2. 是否能被主模型自然续写。
3. 是否存在角色风格混乱、过度夸张或冒犯风险。
4. 是否存在同质化过高的问题。

模板库需要版本化，例如 `templates-v1`，服务响应和日志中记录 `template_id` 与模板版本。

### 4.4 模板抽样与去重

模板选择需要避免高频重复：

1. 按 `locale + persona_tag + filler_type + templates_version` 获取候选模板。
2. 在候选模板内按 `weight` 加权抽样。
3. 对同一用户或同一会话维护短期最近使用模板窗口，例如最近 3 到 5 个 `template_id`。
4. 抽样时优先排除最近窗口内已使用模板；若候选不足，再允许回退到全量候选。
5. 日志记录最终命中的 `template_id`，用于统计模板重复率和模板级体验问题。

交付物：

1. 模板配置文件。
2. 模板审核清单。
3. 模板版本发布记录。
4. 模板抽样与短期去重策略。

## 5. 阶段四：模型训练与导出

### 5.1 选择基础模型

初版建议优先选择 `hfl/rbt3` 作为 base model。该模型是从中文 RoBERTa-wwm-ext 蒸馏得到的 3 层中文模型，兼顾中文语义理解能力和推理延迟，适合作为垫话分类任务的第一版 baseline。

推荐优先级：

| 优先级 | 模型 | 使用场景 |
| :--- | :--- | :--- |
| 首选 | `hfl/rbt3` | 默认 base model，用于建立效果和延迟都较稳的初版 baseline |
| 低延迟备选 | `uer/chinese_roberta_L-4_H-256` | 当 `hfl/rbt3` 量化后仍无法满足延迟预算时使用 |
| 极低延迟备选 | `uer/chinese_roberta_L-2_H-128` | 对延迟极端敏感，且能接受语义效果下降时使用 |
| 效果升级备选 | `hfl/rbt6` | 当 `hfl/rbt3` 离线指标不足，且服务资源允许时使用 |

选择 `hfl/rbt3` 的原因：

1. 中文语义能力更稳：其教师模型使用全词遮蔽预训练，对中文 Query 的语义区分更友好。
2. 推理层数较少：3 层 Transformer 在短文本分类场景中具备较好的 CPU 推理潜力。
3. 分类容量更充足：相比 hidden size 很小的 2 层模型，更适合区分 `ACKNOWLEDGE`、`FRAME`、`THINKING` 等边界接近的类型。
4. 工程路径清晰：可直接微调、导出 ONNX，并通过 dynamic quantization 进一步压缩延迟。

模型目标：

1. CPU 单次分类推理 `< 5ms`。
2. 使用 ONNX Runtime 和量化后，分类服务整体 `p95 < 10ms`。
3. 模型体积尽量控制在 15MB 到 50MB；若使用 `hfl/rbt3` 后体积略高，应以实际延迟和指标为准。
4. 支持导出 ONNX。
5. Tokenizer 和模型推理链路稳定可部署。

决策策略：

1. 先用 `hfl/rbt3` 训练 baseline。
2. 如果 `Trigger Precision`、`Type Macro-F1` 达标且延迟达标，固定为 v1 base model。
3. 如果效果达标但延迟偏高，优先做 ONNX dynamic quantization 和运行时调优。
4. 如果量化后仍无法达标，再降级到 `uer/chinese_roberta_L-4_H-256`。
5. 如果延迟达标但效果不足，再升级到 `hfl/rbt6` 或补充 hard cases 数据后重新训练。

### 5.2 设计分类头

推荐实现方式：

1. 单模型多分类输出：直接预测 `NONE + 六类触发类型`。
2. 后处理阶段将 `NONE` 映射为 `trigger=0`，其他类别映射为 `trigger=1`。

该方式能天然满足 `trigger=0` 时 `filler_type=NONE` 的约束，减少双头模型输出冲突。
它是对“先判断是否触发，再判断触发类型”的工程等价实现：训练和推理阶段只做一次七分类预测，但接口语义仍然对外返回 `trigger` 与 `filler_type` 两个字段。

### 5.3 训练策略

训练时关注：

1. 类别不平衡处理，尤其是 `NONE` 与各触发类型的比例。
2. 加权损失或重采样，避免少数类召回过低。
3. 验证集监控 `Trigger Precision`、`Trigger Recall`、`Type Macro-F1`。
4. 对误触发样本施加更高关注，因为误触发会直接伤害简单问题体验。

### 5.4 离线评估

模型进入导出前需要满足：

1. `Trigger Precision >= 95%`。
2. `Trigger Recall >= 80%`。
3. `Type Macro-F1 >= 85%`。
4. hard cases 回归集无明显退化。
5. 混淆矩阵中 `ACKNOWLEDGE`、`FRAME`、`THINKING` 的混淆率可接受。

### 5.5 导出 ONNX 并优化

导出步骤：

1. 将训练后的模型导出为 ONNX。
2. 使用 ONNX Runtime 验证输出一致性。
3. 根据部署环境评估动态量化或静态量化。
4. 固化 `model_version`，例如 `filler-cls-v1`。
5. 打包模型文件、Tokenizer 文件、标签映射文件和版本元信息。

交付物：

1. 训练代码与配置。
2. 模型评估报告。
3. ONNX 模型包。
4. 标签映射与模型版本说明。

## 6. 阶段五：推理服务实现

### 6.1 定义服务接口

请求格式：

```json
{
  "request_id": "req-001",
  "query": "你怎么看 AI 对教育行业的影响？",
  "persona_tag": "male_white_collar",
  "locale": "zh-CN"
}
```

响应格式：

```json
{
  "trigger": 1,
  "filler_type": "FRAME",
  "filler_text": "关于这个问题，",
  "template_id": "male_white_collar.frame.001",
  "model_version": "filler-cls-v1",
  "confidence": 0.93
}
```

### 6.2 实现推理流程

服务主流程：

1. 校验请求字段，确保 `query` 与 `persona_tag` 必填。
2. 对 Query 做轻量归一化，例如去除首尾空白、统一全半角或重复空格。
3. 使用归一化 Query 和 `model_version` 查询分类缓存。
4. 缓存未命中时执行 Tokenizer 与 ONNX 推理。
5. 将模型类别映射为 `trigger` 和 `filler_type`。
6. 若 `trigger=0`，返回空 `filler_text` 和空 `template_id`。
7. 若 `trigger=1`，根据 `persona_tag + filler_type + locale` 从模板库抽样。
8. 返回结果并记录结构化日志。

### 6.3 缓存策略

分类缓存：

1. Key：`normalized_query + model_version`。
2. Value：`trigger + filler_type + confidence`。
3. Persona 不进入分类缓存 Key。
4. 建议设置容量上限和 TTL，例如按服务实例内存预算配置最大条目数，并使用 LRU 或 TinyLFU 淘汰。
5. TTL 不宜过长，避免模型或归一化策略调整后残留结果影响分析；模型版本升级通过 `model_version` 自然隔离。

模板选择缓存可选：

1. Key：`persona_tag + filler_type + locale + templates_version`。
2. Value：可用模板列表或预加载模板索引。
3. 模板缓存需要随 `templates_version` 隔离，模板版本发布后可主动预热。

注意事项：

1. 缓存命中不能绕过模板版本。
2. 模型版本升级后需要自然隔离缓存。
3. 高频 Query 适合预热缓存。
4. 缓存指标需要记录命中率、容量使用率、淘汰次数和缓存查询耗时。

### 6.4 异常与降级

建议降级策略：

1. Query 为空或过短：返回 `trigger=0`。
2. Persona 不存在：使用默认 Persona 或返回可观测错误，具体由产品策略决定。
3. 模型推理失败：返回 `trigger=0`，避免错误垫话影响用户体验。
4. 模板缺失：返回 `trigger=0` 或使用同 Persona 的通用模板，需记录告警。

交付物：

1. 推理服务代码。
2. API 文档。
3. 缓存与配置加载实现。
4. 结构化日志与错误码定义。

## 7. 阶段六：性能优化与压测

### 7.1 单请求延迟优化

需要分别统计：

1. 请求解析耗时。
2. Query 归一化耗时。
3. 缓存查询耗时。
4. Tokenizer 耗时。
5. ONNX 推理耗时。
6. 模板选择耗时。
7. 总响应耗时。

目标指标：

1. 分类服务整体 `p95 < 10ms`。
2. 分类服务整体 `p99 < 20ms`。
3. CPU 高并发下 p99 不明显劣化。
4. 联调链路中，从 ASR 输出完整 Query 到垫话 TTS 首个可播放音频帧，建议 `p95 < 200ms`。

### 7.2 并发压测

压测计划：

1. 使用真实 Query 长度分布构造压测集。
2. 分别测试缓存命中率为 0%、50%、90% 的场景。
3. 覆盖目标 QPS、2 倍目标 QPS 和峰值突增场景。
4. 记录 CPU、内存、线程池、ONNX Runtime 会话和请求队列指标。

### 7.3 模型与运行时优化

可选优化手段：

1. ONNX Runtime CPU execution provider。
2. 线程数、batch 策略和 session 复用调优。
3. 模型量化。
4. 高频短 Query 规则快路径，但规则必须保守，避免引入复杂分支。

交付物：

1. 压测脚本。
2. 性能报告。
3. 延迟分解报表。
4. 推荐部署规格。

## 8. 阶段七：联调与体验验收

### 8.1 与下游系统联调

联调重点：

1. 下游将 `filler_text` 作为主回复已播放前缀处理。
2. 主模型续写需要避免重复输出同一前缀。
3. TTS 可以在垫话返回后立即合成并播放。
4. 垫话播放结束前，主模型后续音频缓冲区应尽量就绪。

联调指标：

1. 快路径首音频延迟：从 ASR 输出完整 Query 到垫话 TTS 首个可播放音频帧，建议 `p95 < 200ms`。
2. `buffer_ready_rate`：垫话播放结束时主回复音频缓冲区已有可播放音频帧的比例，建议 `>= 95%`。
3. 重复前缀去重成功率：下游主模型输出包含同一前缀时，应在播放或合成前完成去重。

### 8.2 人工体验评估

抽样评估维度：

1. 垫话是否该出现。
2. 垫话类型是否合适。
3. Persona 风格是否自然。
4. 垫话与主回复续写是否连贯。
5. 是否出现重复、割裂或语气不一致。

上线前建议达到：

1. 垫话自然度平均分 `>= 4.2 / 5`。
2. 续写连贯性通过率 `>= 95%`。
3. 重复与割裂率 `< 2%`。

### 8.3 在线 A/B 实验

建议灰度指标：

1. 用户打断率。
2. 首轮继续对话率。
3. 负反馈率。
4. 平均感知等待时长。
5. `buffer_ready_rate`，上线门槛建议 `>= 95%`。
6. 不同 Persona 和不同 Query 类型下的触发分布。

实验组应降低感知等待，同时不能显著提升打断率或负反馈率。

交付物：

1. 联调测试用例。
2. 人工评估报告。
3. A/B 实验方案与指标看板。

## 9. 阶段八：灰度上线与迭代机制

### 9.1 灰度发布

推荐发布顺序：

1. 仅日志模式：服务返回结果但不播放垫话，用于观察分布。
2. 内部用户灰度：开启真实播放，收集主观反馈。
3. 小流量线上灰度：按用户、场景或 Persona 分桶。
4. 扩大流量：在指标稳定后逐步放量。
5. 全量上线：保留快速回滚开关。

### 9.2 线上监控

必须监控：

1. 请求量、错误率、超时率。
2. p50、p95、p99 延迟。
3. 缓存命中率。
4. 各 `filler_type` 触发分布。
5. 各 Persona 模板命中分布。
6. 模板重复率。
7. 下游反馈的重复播放、语义割裂和用户打断事件。

### 9.3 迭代闭环

建议每轮迭代流程：

1. 从线上日志采样误触发、漏触发和类型错误样本。
2. 加入人工复核池。
3. 更新 hard cases 集。
4. 重新训练并评估模型。
5. 灰度发布新 `model_version`。
6. 对比新旧版本离线与在线指标。

交付物：

1. 灰度发布方案。
2. 线上监控看板。
3. 回滚预案。
4. 模型与模板迭代流程。
